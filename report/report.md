## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

本次实验主要围绕已有最小内核的启动过程展开。首先，构建系统通过交叉编译和链接生成内核，链接脚本确定代码、数据和启动栈的位置，并产生用于调试的 `bin/kernel` 和用于装载的 `bin/ucore.img`。QEMU 启动时建立虚拟硬件环境，装入 OpenSBI，并按照 Makefile 中的 loader 参数将内核镜像预先放到 `0x80200000`。

CPU 从 `0x1000` 的复位 ROM 代码开始执行，随后跳转到 `0x80000000`，进入 OpenSBI。OpenSBI 完成底层初始化后，将控制权交给位于 `0x80200000` 的 ucore 入口 `kern_entry`。入口汇编先设置内核自己的栈，再跳转到 C 函数 `kern_init`。该函数根据链接边界处理需要清零的数据区域，通过 SBI 控制台服务输出启动信息，最后进入无限循环。

这条路线需要结合源码和调试结果来理解。阅读源码可以知道每个阶段打算完成什么，通过 GDB 查看 PC、指令和栈指针，则可以核对 CPU 实际执行到了哪里、哪些状态发生了变化。遇到地址来源不明确的符号，还需要回到链接脚本和符号表中查找定义。

### 2.2 功能的逐步实现

| 阶段 | 主要作用 | 与后续阶段的关系 |
|---|---|---|
| 编译与链接 | 生成 RISC-V 内核代码，确定各段和符号的地址 | 为镜像装载和运行提供内存布局 |
| QEMU 装载与复位 | 建立虚拟硬件环境，装入固件和内核镜像 | 使 CPU 能从复位地址取到启动指令 |
| OpenSBI 初始化 | 完成底层初始化，提供 SBI 服务，并交接到内核 | 为内核运行和控制台输出提供基础 |
| `kern_entry` | 将 `sp` 设置为内核栈顶，再跳转到 `kern_init` | 为 C 函数调用准备可用的栈 |
| `kern_init` | 处理数据初始化、打印启动信息并进入无限循环 | 完成最小内核的启动，呈现可观察的运行结果 |

这些阶段前后衔接。例如，栈的位置需要先在链接时确定，入口代码才能取得栈顶地址；设置好栈之后，后续的 C 函数调用才能使用这块空间。本实验主要通过阅读和调试已有代码，理解这些依赖关系。

### 练习：Exercise 1——理解内核启动中的程序入口操作

**负责人：** 徐夏茗

#### 入口代码与启动栈

本练习分析已有的 [entry.S](../code/kern/init/entry.S)，主要理解设置内核栈和进入 C 函数这两项操作。完整源码如下：

看到 `kern_entry` 中的 `la sp, bootstacktop` 后，我先理解为：这条指令要把 SP 改为指向 `bootstacktop`，让内核开始使用自己的栈。接下来需要解释的是，这个栈顶的位置怎样确定。因此，我先沿着 `entry.S` 中的标签往下读，再查头文件中的大小定义和链接脚本中的布局，推导出栈顶地址，最后用反汇编和 GDB 核对。

```asm
#include <mmu.h>
#include <memlayout.h>

    .section .text,"ax",%progbits
    .globl kern_entry
kern_entry:
    la sp, bootstacktop

    tail kern_init

.section .data
    # .align 2^12
    .align PGSHIFT
    .global bootstack
bootstack:
    .space KSTACKSIZE
    .global bootstacktop
bootstacktop:
```

`.section .text` 指定后续入口代码放入代码段；`.globl` 和 `.global` 使对应符号可被其他文件引用。`kern_entry`、`bootstack` 和 `bootstacktop` 都是位置标签，它们的地址由汇编和链接布局确定，标签本身不额外占用存储空间。

沿着 `bootstacktop` 查找，可以看到它位于下半部分的 `.data` 中。往前读，先是 `.align PGSHIFT`，然后是 `bootstack:`，中间通过 `.space KSTACKSIZE` 预留空间，最后才到 `bootstacktop:`。

这里还需要查清两个宏：`PGSHIFT` 决定对齐要求，`KSTACKSIZE` 决定预留多少字节。继续查看 [mmu.h](../code/kern/mm/mmu.h) 和 [memlayout.h](../code/kern/mm/memlayout.h)，得到：

```c
#define PGSIZE      4096
#define PGSHIFT     12
#define KSTACKPAGE  2
#define KSTACKSIZE  (KSTACKPAGE * PGSIZE)
```

因此，`.align PGSHIFT` 要求接下来的栈起点按 `2^12=4096` 字节对齐；`.space KSTACKSIZE` 则预留 `2×4096=8192` 字节，即 `0x2000` 字节。这里要把对齐单位和空间大小分开：一页是 4096 字节，这块栈有两页。这样已经可以推得相对位置关系：

```text
bootstacktop = bootstack + 0x2000
```

但仅靠这个关系，还不知道绝对地址。我接着去看 [kernel.ld](../code/tools/kernel.ld)：脚本先通过 `. = BASE_ADDRESS` 从 `0x80200000` 开始安排 `.text`，接着安排 `.rodata`，然后执行 `. = ALIGN(0x1000)`，再安排 `.data`。因此，`.data` 的基址要由前面内容的结束位置和对齐要求共同确定，不能直接拿内核基址代替。

接下来需要知道前面各节实际占了多少空间。这里的 `bin` 是构建输出目录，`kernel` 是链接后生成的 ELF 二进制文件，普通文本编辑器不能直接把它显示成代码和布局表。因此，需要用能够读取 ELF 结构的工具查看。在实验容器的 `/home/OS/lab1/code` 目录中执行：

```sh
riscv64-unknown-elf-readelf -SW bin/kernel
```

`readelf` 用来查看 ELF 文件中的信息，`-S` 显示节表，`-W` 使用宽行输出，便于把同一节的信息放在一行里阅读。对当前已有 `bin/kernel` 实际执行该命令，相关输出节选如下：

```text
  [Nr] Name              Type            Address          Off    Size   ES Flg Lk Inf Al
  [ 1] .text             PROGBITS        0000000080200000 001000 0004c0 00  AX  0   0  2
  [ 2] .rodata           PROGBITS        00000000802004c0 0014c0 000270 00   A  0   0  8
  [ 3] .data             PROGBITS        0000000080201000 002000 002000 00  WA  0   0 4096
```

读这份输出时，先看 `Name` 找到要分析的节，再看 `Address` 和 `Size`：前者是链接后的内存起始地址，后者是该节的字节数，两列都按十六进制显示。`Off` 表示这部分内容在 ELF 文件中的偏移，不能拿它当作内存地址；`Al` 表示字节对齐要求，比如 `.data` 这一行的 `4096`。因此，表里的起点和大小来自实际节表，而结束边界还需要自己相加得到：

```text
.text   结束边界 = 0x80200000 + 0x4c0 = 0x802004c0
.rodata 结束边界 = 0x802004c0 + 0x270 = 0x80200730
```

据此，前两部分的布局为：

| 输出节 | 起始地址 | 大小 | 结束边界 |
|---|---|---|---|
| `.text` | `0x80200000` | `0x4c0` | `0x802004c0` |
| `.rodata` | `0x802004c0` | `0x270` | `0x80200730` |

前面的内容结束于 `0x80200730`，向上对齐到 `0x1000` 字节边界后，得到 `.data` 起点 `0x80201000`。当前构建中，`bootstack` 恰好位于 `.data` 的起点，因此再加上预留的栈空间，就能算出：

```text
bootstack    = 0x80201000
bootstacktop = 0x80201000 + 0x2000
             = 0x80203000
```

到这里，`bootstacktop` 的来源就清楚了，于是就可以回答一下问题：

#### 问题 1：`la sp, bootstacktop` 完成什么操作，目的是什么？

`la` 表示加载地址，这条伪指令将 `bootstacktop` 的地址放入栈指针寄存器 `sp`。它取得的是标签的地址，不是该地址中存放的数据。栈向低地址增长，所以初始 SP 指向预留空间的高地址边界。

其目的是让 ucore 开始使用自己预留的栈，为后面的 C 函数调用准备可用空间。OpenSBI 运行时也使用自己的栈，进入内核时留下的 SP 不能直接当成内核启动栈。函数调用保存寄存器和局部状态时，需要使用由内核管理的栈区域。

讨论这一点时，我的初步理解是：OpenSBI 和内核各自管理自己的状态，混用栈可能让保存和恢复的状态相互覆盖。这个方向是对的，但在和大模型讨论中发现还需要补充，OpenSBI 在交接后仍能被内核通过 SBI 调用，处理服务请求时，涉及的是本次调用的上下文保存和恢复，不能理解为恢复启动时留下的**全部状态**。

根据前面分析可知，执行 `la sp, bootstacktop` 后，SP 应变为 `0x80203000`。

**GDB 验证：SP 是否指向内核栈顶**

这一步要核对的是问题 1 中的预测：执行 `la sp, bootstacktop` 后，SP 是否变为栈顶地址 `0x80203000`。

以下记录来自本次保存的 [GDB 日志](assets/gdb-startup-20261010.log)。

在前面的调试中，我曾看到入口处的 SP 为 `0x8001dd30`，与手册不一样，因此怀疑是不是执行了不同的内核汇编。继续核对时，需要先分清“停在这条指令上”和“已经执行完这条指令”：断点停在 `kern_entry` 的第一条指令前，内核还没有设置 SP，这个值反映的是固件留下的状态。固件版本和构建布局会影响这个状态，因此要同时核对固件版本、PC 和附近的机器指令。下面使用当前 OpenSBI v0.4 的记录，再检查入口指令执行后的 SP 是否与内核栈顶一致。

在 `kern_entry` 设置断点并继续运行后，GDB 停在 `0x80200000`。此时入口指令尚未执行，SP 仍然是固件运行后留下的值：

```text
(gdb) info registers pc sp
pc             0x80200000   0x80200000 <kern_entry>
sp             0x8001bd80   0x8001bd80
```

当前 `la sp, bootstacktop` 对应两条机器指令，因此使用 `si 2` 执行这两条指令，再查询寄存器：

```text
(gdb) si 2
9       tail kern_init
(gdb) info registers pc sp
pc             0x80200008   0x80200008 <kern_entry+8>
sp             0x80203000   0x80203000 <SBI_CONSOLE_PUTCHAR>
```

此时 PC 已到 `0x80200008`，下一条是尚未执行的 `tail kern_init`，SP 则已经从 `0x8001bd80` 变为 `0x80203000`。同一记录中，`p/x &bootstacktop` 的结果也是 `0x80203000`，与切换后的 SP 一致。

#### 问题 2：`tail kern_init` 完成什么操作，目的是什么？

我先把这条指令理解为：进入 `kern_init` 执行，但不为这次转移保存新的返回地址。普通函数调用除了改变 PC，还要记住执行结束后回到哪里；例如一条 4 字节的 `jal ra, ...` 会把自身地址加 4 保存到 `ra`，也就是下一条指令的地址。`tail` 是 RISC-V 的尾调用伪指令，它把控制权交给目标函数，不改写 `ra`，因此不会建立一个返回到当前调用位置的新地址。这里应记住的是“下一条指令的地址”，不能把所有调用的返回地址都固定理解为 PC+4。

接下来结合 `init.c` 中的声明和函数结尾来看：

```c
int kern_init(void) __attribute__((noreturn));

// kern_init 的函数结尾
while (1)
    ;
```

经过查阅发现，这个特殊属性`noreturn` 会告诉编译器函数不会正常返回到调用者，函数末尾的无限循环也与这个声明一致；而这次转移是否写入返回地址，要看调用处实际使用的指令。属性本身不会让 CPU 自动跳过保存返回地址的操作，`tail` 本身也不保证目标函数不会返回。

回到当前构建的 [反汇编](../code/obj/kernel.asm)，`tail kern_init` 对应：

```asm
80200008: a009        j     8020000a <kern_init>
```

执行 `la` 后，SP 已指向内核自己的栈顶。随后，`tail kern_init` 对应的跳转将 PC 转到 `0x8020000a`，CPU 从这里开始执行由 C 初始化函数编译出来的机器指令，`ra` 不被改写。进入 `kern_init` 后，它使用前面设置的内核栈，完成清零、打印，最后进入无限循环，不会返回到 `kern_entry`。因此，汇编入口的工作在这次跳转后就结束了，后续执行流程留在 `kern_init` 中。

### 练习：Exercise 2——使用 GDB 验证启动流程

**负责人：** 焦宇堃、黄国天

#### 从当前 PC 开始分析

练习一已经分析了内核入口的两条指令，但 CPU 刚启动时，还没有执行到 `kern_entry`。这一部分需要从最初的 PC 出发，查看它正在执行的指令，再沿着跳转找到内核入口。

调试时，左侧终端运行 `make debug`，右侧运行 `make gdb`。查看 Makefile 可以知道，`-S` 让 CPU 在启动时暂停，`-s` 开启默认端口 1234 的 GDB 服务；当前 `make gdb` 已经完成读取 `bin/kernel`、设置架构和连接目标。下面使用此前 OpenSBI v0.4 环境下的调试记录展开分析。

#### 问题 1：最初执行的几条指令位于什么地址？

我最初以为刚启动时执行的就是 OpenSBI，但查看 PC 后发现，它停在 `0x1000`，与 OpenSBI 的起始地址 `0x80000000` 不同。为了知道这段代码在做什么，接着用 `x/5i $pc` 查看当前位置开始的五条指令：

```text
(gdb) info registers pc
pc             0x1000   0x1000
(gdb) x/5i $pc
=> 0x1000:     auipc   t0,0x0
   0x1004:     addi    a1,t0,32
   0x1008:     csrr    a0,mhartid
   0x100c:     ld      t0,24(t0)
   0x1010:     jr      t0
```

这里可以先确定，最初执行的五条指令位于 `0x1000` 至 `0x1010`，最后一条是通过 `t0` 跳转。本次 QEMU `virt` 平台在这个位置放置了复位 ROM 代码，CPU 执行完它后才进入 OpenSBI。接下来要弄清楚的就是：`t0` 中的跳转目标从哪里来？

#### 问题 2：这些指令主要完成什么工作？

沿着指令顺序分析，可以得到下面的变化：

| 指令 | 本次执行中的作用 |
|---|---|
| `auipc t0,0` | 当前指令地址加上 `0 << 12`，得到 `t0=0x1000` |
| `addi a1,t0,32` | 得到 `a1=0x1020`，准备交给下一阶段的启动参数 |
| `csrr a0,mhartid` | 将当前硬件线程编号读入 `a0` |
| `ld t0,24(t0)` | 从 `t0+24` 指向的内存中读取 8 字节数据，放入 `t0` |
| `jr t0` | 将 PC 转到 `t0` 中保存的地址 |

我在讨论中一度把 `0x1018` 当成了 `jr` 要跳到的地址。继续看 `ld` 才发现，这里有两步：先算出读取数据的位置，再把读出的数据当作跳转目标。偏移 `24` 是十进制，对应十六进制的 `0x18`，因此读取位置为：

```text
t0 + 24 = 0x1000 + 0x18 = 0x1018
```

为了核对这个位置到底存了什么，用 `x/gx` 读取一个 8 字节数值，再用 `si 5` 执行前面的五条指令：

```text
(gdb) x/gx 0x1018
0x1018:       0x0000000080000000
(gdb) si 5
0x0000000080000000 in ?? ()
(gdb) info registers pc
pc             0x80000000   0x80000000
```

读数是 `0x80000000`，单步后的 PC 也是这个地址，两者对上了。也就是说，`ld` 从 `0x1018` 取出目标地址，覆盖 `t0`，随后 `jr` 跳到 OpenSBI。这几条复位指令的主要工作，就是准备启动参数并进入固件，还没有执行 ucore 的入口代码。

#### 从 OpenSBI 继续找到内核入口

到达 `0x80000000` 后，再查看当前位置的指令，调试记录中的前两条是：

```text
(gdb) x/8i $pc
=> 0x80000000: csrr a6,mhartid
   0x80000004: bgtz a6,0x80000108
```

这里再次读取硬件线程编号，再根据编号选择执行路径。由于我学过一些 LoongArch 汇编，开始时尝试用熟悉的指令理解 `csrr`，把它想成了交换操作。核对后才明确，`csrr a6,mhartid` 是把 `mhartid` 读到 `a6`，不会把 `a6` 的原值写回去。当前 hart 编号为 0，因此按指令含义可以推得 `a6=0`，`bgtz` 的条件不成立，应继续执行 `0x80000008`；这一步是根据指令推断的，已有记录没有在执行后单独查询 `a6`。

继续分析启动流程时，需要确认 OpenSBI 最后有没有进入内核。因此在 `kern_entry` 设置断点，再用 `c` 继续运行：

```text
(gdb) b *kern_entry
Breakpoint 1 at 0x80200000: file kern/init/entry.S, line 7.
(gdb) c

Breakpoint 1, kern_entry () at kern/init/entry.S:7
7       la sp, bootstacktop
(gdb) info registers pc sp
pc             0x80200000   0x80200000 <kern_entry>
sp             0x8001bd80   0x8001bd80
```

PC 已到 `0x80200000 <kern_entry>`，而且 GDB 显示下一条就是设置内核栈的 `la`。这时可以确认，执行流程已经从固件进入了 ucore。断点停在指令执行前，因此这里的 SP 仍是 OpenSBI 留下的值；执行 `la` 后的变化已经在练习一中分析。

内核为什么位于 `0x80200000`，还需要把地址与构建配置对应起来：链接脚本中的 `BASE_ADDRESS` 是 `0x80200000`，Makefile 的 `-device loader,file=$(UCOREIMG),addr=0x80200000` 也把镜像放在这里。本次是 QEMU 预先装入内核，OpenSBI 初始化后交接到它，并没有通过 U-Boot，也不能把这个过程理解成 OpenSBI 从磁盘读取内核。

这样，启动路线就能与实际观察对应起来：`0x1000` 的复位 ROM → `0x80000000` 的 OpenSBI → `0x80200000` 的 `kern_entry`。本次通过单步核对了第一段跳转，通过断点确认了内核入口，没有逐条跟踪 OpenSBI 的全部初始化指令。

#### 继续阅读 `kern_init`

到内核入口后，再结合 [init.c](../code/kern/init/init.c) 看它接下来做什么：

```c
int kern_init(void) __attribute__((noreturn));

int kern_init(void) {
    extern char edata[], end[];
    memset(edata, 0, end - edata);

    const char *message = "(THU.CST) os is loading ...\n";
    cprintf("%s\n\n", message);
    while (1)
        ;
}
```

看到 `memset(edata, 0, end - edata)` 时，我先理解为给一块内存清零，但还不知道这块内存的范围怎么确定。因此又去查了 [链接脚本](../code/tools/kernel.ld)，在其中找到：

```ld
    PROVIDE(edata = .);

    .bss : {
        *(.bss)
        *(.bss.*)
        *(.sbss*)
    }

    PROVIDE(end = .);
```

前面的 `.data`、`.sdata` 排完后，`edata` 记录当时的位置；`.bss` 排完后，`end` 再记录一次位置。两者相减就是 `[edata, end)` 的长度，对应这里要清零的范围，BSS 中需要零初值的数据也包含在其中。这样再回看 `memset`，就能知道它的地址和长度分别从哪里来。

此前 GDB 记录中，`edata` 和 `end` 都是 `0x80203008`，所以当前构建的清零长度为 0。这也提醒我，理解代码的用途后，还要查当前镜像的实际布局，不能直接假定这次一定有一块非空 BSS 等着清零。

接着是 `cprintf` 打印启动信息。沿源码查看，格式化后的字符经 `cons_putc`、`sbi_console_putchar`，最后通过 `ecall` 请求 OpenSBI 的控制台服务。因此 OpenSBI 把执行流程交给内核后，仍能为内核提供服务。此前 GDB 分离后，QEMU 终端出现：

```text
(THU.CST) os is loading ...
```

这条输出说明内核已经执行到了 C 初始化函数中的打印操作，与前面的入口断点对应上了。

## 五、实验总结与收获

### 对操作系统的理解

#### 1. 本实验的重要知识点及其与 OS 原理的联系

**内核启动流程与入口地址。** 操作系统启动需要先建立基本运行条件，再进入内核。在本实验中，CPU 从 `0x1000` 的复位 ROM 开始执行，通过 `ld` 取得目标地址，再由 `jr` 跳到 `0x80000000` 的 OpenSBI。固件初始化后，执行流程进入 `0x80200000` 的 `kern_entry`。这对应 OS 原理中的引导过程，不过本次内核镜像由 QEMU loader 预先装入，不能直接套用从磁盘读取内核的启动方式。

**汇编入口为 C 函数准备栈。** 函数调用需要使用栈保存寄存器和局部状态，内核进入 C 初始化前也要准备自己的栈。`entry.S` 用 `.space KSTACKSIZE` 预留空间，再通过 `la sp, bootstacktop` 设置栈指针。沿着宏定义和链接布局推导，再与 GDB 中的 SP 比较，可以确认这次切换到了内核启动栈。这里对应栈和函数调用的原理，还没有涉及进程之间的上下文切换。

**尾调用与控制流转移。** 普通调用需要建立返回地址，`tail kern_init` 则将执行流程转到初始化函数，不改写 `ra`。当前机器代码是一条直接跳转，结合 `kern_init` 的 `noreturn` 声明和末尾空循环，可以知道它不会再返回入口。这对应函数调用与尾调用的机制，但需要分清：不建立新的返回地址由调用指令决定，函数不会返回则要结合目标函数分析，不能把两者混为一谈。

**内存布局、符号与对齐。** 代码、数据和启动栈的位置需要在链接时确定，源码再通过符号引用这些位置。`bootstacktop` 的地址要结合栈大小和 `.data` 布局推导，`.align PGSHIFT` 则给出栈起点的对齐要求；`.global` 只是让符号可以被其他文件引用，不会给它分配地址。继续阅读 `edata` 和 `end` 时，也需要用链接脚本确定清零范围。这些内容对应程序装载、内存布局和静态数据初始化，还没有涉及页表或虚拟内存管理。

#### 2. OS 原理中重要但本实验尚未涉及的知识点

**进程调度与管理。** 操作系统需要管理多个进程，保存和恢复执行上下文，并通过调度分配 CPU 时间。本实验只有最小内核的启动流程，打印后的空循环没有实现任务调度。

**文件系统。** 文件系统负责组织和访问持久化数据，涉及文件、目录以及存储设备的管理。本实验只装入内核镜像并输出启动信息，没有涉及文件读写。

**中断与异常处理。** 操作系统需要响应设备中断和执行异常，完成现场保存、处理与返回。本次通过 `ecall` 请求了固件服务，但还没有实现 ucore 自己的完整中断和异常处理流程。

**虚拟内存与分页。** 虚拟内存通过页表完成地址映射，并提供访问保护等功能。本实验中的页大小和对齐用于确定内存布局，还没有建立页表，也没有涉及缺页处理或页面置换。

**用户态与内核态切换。** 用户程序通过系统调用请求内核服务，特权级限制则用于保护内核和其他程序。本实验没有运行用户程序；内核请求 OpenSBI 服务，也不能等同于已经实现用户态系统调用。
